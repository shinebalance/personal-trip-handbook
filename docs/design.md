# 韓国旅行しおり：初期設計案

作成日：2026-09-22。実装時の決定を反映。実装と更新手順は README.md を参照。公開設定・地図キーの登録は別途行う。

## 1. 目指す体験

Markdownを追加して育てる、個人用のビジュアルな旅のしおり。現地でスマホを開き、「何をしたかったか」「どこへ向かうか」「友人にどう伝えるか」をすぐ確認できる。PCでは旅全体を見渡して計画できる。

GitHub Pages上で完結する静的サイトとし、閲覧時のサーバーやデータベースは設けない。Markdownの追加・編集をGitHubにpushすると、ビルドで画面用データを生成して公開する。

## 2. 現在のメモから読み取れること

- 弘大、延禧洞、龍山、光化門など、エリア別に回りたい場所がある。
- 「行けたら」「時間に余裕があれば」「見かけたら」という条件を保持する必要がある。無条件の項目を勝手に「必須」にしない。
- 店舗、街全体、チェーン、料理、商品が混在している。料理や商品に架空の所在地を割り当てない。
- HOTTRACKSは行き先と買い物の両方に登場する。同一施設の参照と購入目的を関連付ける。
- 国際電子センターはMarkdown上では延禧洞の見出しの下にあるが、そのエリア所属が正しいとは限らない。場所の確認までエリア未確定として扱う。
- 日程と多くの店舗情報は未入力。宿泊情報は公開しない。ファイル名の日付を旅行日と解釈しない。
- 食品の流行などの記述はユーザーのメモとして保持し、確認済みの旅行情報として言い換えない。

## 3. 画面構成

スマホの主な移動先は「行き先」「食・買い物」「旅程」「メモ」の4つ。行き先画面がホームを兼ね、地図プレビューは詳細パネルから利用する。

| 画面 | 内容・操作 |
| --- | --- |
| ホーム | 旅のタイトル、日程があれば旅行期間と当日の予定、エリア一覧、行きたい場所の抜粋、候補へのショートカット |
| 行き先 | エリア・カテゴリ・希望条件で絞り込み、キーワード検索、カード一覧 |
| 食・買い物 | 料理や商品を写真・イラスト・短い説明で一覧化。店が決まったらスポットに関連付ける |
| 旅程 | 日付別のタイムライン。時間未定の予定も置ける。スポットを参照する |
| スポット詳細 | 日本語名・韓国語名、訪問理由、住所、参考リンク、Google Mapsを開く、住所コピー、地図プレビュー |
| メモ | 元のMarkdownを読みやすく表示。タブからアクセスし、カードにまだ整理していない内容も読める |

日程のない初期状態では「今日の予定」を無理に表示せず、エリア一覧と行き先を主役にする。ホテル情報は掲載しない。

PCではカードを複数列にし、詳細を右側に表示できる。スマホではカードから詳細パネルを開く。戻ったときに絞り込みとスクロール位置を維持する。

## 4. 見た目の方向性

「旅の雑誌と街歩きのノート」をイメージする。薄いグリーンを基調に、白いハイライトとやわらかな陰影を重ねるネオモーフィズムを採用する。文字は読みやすい濃さを確保する。

カードには「場所の名前」「韓国語名」「行きたい理由」「エリア」「地図ボタン」を優先して載せる。写真は見出しや主要カードに絞り、情報密度と読みやすさを保つ。写真がない場所はカテゴリ別の図形やイラストで整え、別店舗の写真を代用しない。

スマホでは親指で押しやすいボタン、十分な文字サイズ、色だけに依存しない状態表示を採用。アニメーションは控えめにし、日韓英いずれの文字でも読みやすいフォントと余白を選ぶ。

## 5. Markdownを中心にした更新方法

自由なメモと、構造化した情報の2段階で運用する。すべての自由記述を自動で正確な店舗カードに変換する設計にはしない。ビルド時にAIや外部サービスを必要とせず、同じ入力から同じサイトが生成されるようにする。

### 自由なメモ

今のようなMarkdownはそのまま `mds/` に追加できる。見出し・箇条書き・リンクを保持したメモページとして掲載し、検索対象にする。新しい書き方を覚えなくても情報が失われない。

### 整理済みの情報

カード化したい情報にはMarkdown冒頭に小さなYAMLメタデータ（frontmatter）を付ける。本文は引き続き自由に記述する。スポット、食・買い物、日程のテンプレートを用意する。

以下は未調査の入力例。未確認の住所やリンクは省略する。

```md
---
type: spot
id: thanks-books
title: THANKS BOOKS
area: hongdae
category: books
priority: candidate
koreanName: 땡스북스
---
独立系書店を見たい。
```

必須項目は `type`・`id`・`title` に絞る。住所や画像のない段階でもカードにできる。住所未確認なら確定した目的地として案内せず、店名検索リンクには「地図で検索」と明記する。

| 種別 | 主な情報 |
| --- | --- |
| spot | 店舗・施設・街、エリア、カテゴリ、支店、韓国語名、住所、地図URL、任意の座標、希望条件 |
| wish | 食べたいもの・買いたいもの、カテゴリ、関連するspotのID |
| day | 日付、時間または時間帯、予定の説明、関連するspotのID |
| note | 自由記述メモ。frontmatterなしもこの扱い |

希望条件は「候補」「行けたら」「見かけたら」などを保存する。訪問済み状態とは分離する。重複は名前だけで自動統合せず、安定したIDで参照する。

初回実装では現在のメモを人が確認できる形でカード用Markdownに整理し、原文も残す。以後の追加分は、自由メモとして即掲載するか、テンプレートでカード化するかを選べる。

```text
mds/
  2026-09-22_韓国旅行メモ.md
  spots/
    thanks-books.md
  wishes/
    foods.md
  days/
    day-01.md
public/images/
src/
scripts/                 # Markdownの検証・変換
docs/design.md
```

これは拡張時の配置例。初期の整理済み情報は `mds/spots.md` と `mds/wishlist.md` にまとめてある。

## 6. 地図とリンク

初期版では各スポットのGoogle Mapsリンクと住所コピーを必須の導線とする。確認済みの場所URLがなければ検索URLを生成する。Maps URLsはAPIキーなしで利用できる。

地図プレビューは詳細を開いた時にだけ読み込む。自動生成するGoogle Maps Embed API方式にはAPIキーの準備が必要。採用時は利用API・公開サイトの参照元を制限する。地図が読み込めない場合も名称・住所・外部リンクは使えるようにする。

初期版の推奨範囲は「選んだスポットの地図プレビュー」まで。全スポットを一枚の地図にピン表示する機能は、座標整備と地図ライブラリ／サービスの選定が必要なため次段階とする。APIキー準備前でも、カードと外部地図リンクだけで運用開始できる。

韓国の友人に共有しやすいように、NAVER Map・Kakao Mapの確認済みURLも任意で登録できる構造にする。すべての店に自動で正しい支店リンクが付くとは想定しない。

## 7. 日本語・韓国語・英語と共有

初期版から日本語・韓国語・英語を切り替える。UI・整理済みカードの名前・訪問理由は3言語対応。店舗名・住所には韓国語を併記する。追加情報の翻訳を省略した場合は日本語を表示し、自由メモは原文を維持する。

スポットや旅程には直接共有できるURLを用意する。友人が同じスポットを開けることを優先する。翻訳は閲覧時の外部APIに依存しない。

一般的なGitHub Pages公開ではサイトはインターネットから閲覧可能。個人用という意味は用途の個人用であり、本人だけが読める仕組みにはならない。予約番号、パスポート情報などは公開用Markdownに含めない。ホテル名や宿泊日も掲載しない。画面で隠すだけでは公開データの保護にならない。

## 8. 技術構成

推奨：React + TypeScript + Vite、Markdownパーサー、ビルド時のスキーマ検証、GitHub ActionsによるGitHub Pagesへの配置。

1. `mds/**/*.md` をビルド時に収集。
2. frontmatterと本文を解析し、型・ID・参照先を検証。
3. 画面用JSONと安全な本文表示データを生成。
4. Reactが検索・絞り込み・表示切り替えを担当。
5. 生成された静的ファイルだけをPagesに配信。

Markdown内の任意HTMLやスクリプトは実行しない。未知のtypeや重複IDなどはファイル名付きのエラーにし、任意項目の欠落は未入力として許容する。不正な更新は公開せず、直前のサイトを維持する。

プロジェクト名を含むPagesのサブパスに対応し、共有URLは当初ハッシュ形式（例：`/#/spots/thanks-books`）を使う。直接アクセス・再読み込みでもサーバー側ルーティングを必要としない。

「行った」「買った」のチェック状態は任意機能としてlocalStorageに保存可能。ただしスマホとPC、友人との間で同期されない。共有したい状態はMarkdownで管理する。

オフライン対応は次段階でService Workerを追加し、閲覧用データと画面をキャッシュする。外部地図・外部ページはオフライン利用できるとは約束しない。

## 9. 実装の順序

1. 現在のメモをもとにカード一覧・詳細・エリア絞り込みを作り、スマホの見た目を確認する。
2. Markdown読込、自由メモ表示、テンプレート、入力検証を接続する。
3. スポットの支店・住所・リンクを確認し、韓国語名と地図導線を整備する。
4. 追加された情報を表示できる旅程画面を実装する。
5. 共有URL、日韓英表示、Pagesの公開設定を整備する。
6. 地図プレビュー、訪問チェック、オフライン対応を必要に応じて拡張する。

初期版の完成条件：スマホで候補を一覧できる／確認済みの場所の地図をすぐ開ける／任意のMarkdown追加で情報が掲載される／旅程を後から追加できる／共有URLが直接開く／Pagesのサブパスで動作する。

## 10. 今後確認する情報

設計・画面試作は現状の情報で開始できる。旅程の完成には旅行日程が必要。場所の案内を正確にするため、チェーンや曖昧な店名は支店を確定する。地図キーはGitHub Secretsからビルド時に渡す。公開後のブラウザでキーは見えるため、参照元とMaps Embed APIへの制限が必要。
